## 产品形态：本地软件（可拓展）

做成**安装/启动在本机的软件**，而不是公网网站。原因：

- ASR 等模型在本地 GPU 上跑，体积大，需要启动时做**是否存在 / 是否完整 / 能否加载**的检测
- 缺模型时要能提示路径、引导下载或选择替代模型，而不是跑到一半才报错
- 后续还会加需求 2、更多积木与模型，需要统一的「运行时外壳」

### 软件分层（方便拓展）

```
┌─────────────────────────────────────┐
│  渲染进程（React/Vue + TypeScript）   │  工具箱 UI；功能页
└──────────────────┬──────────────────┘
                   │ IPC（或本地 HTTP）
┌──────────────────▼──────────────────┐
│  Electron 主进程（TypeScript）★       │  窗口 + 全部业务
│  - 启动时：环境检测 + 模型检测          │
│  流水线 pipelines / 积木 modules      │
│  运行时 runtime / 货物 artifacts      │
└─────────────────────────────────────┘
```

### 模型与环境（配置页约定）

| 项 | 策略 |
| --- | --- |
| **yt-dlp / ffmpeg** | **随软件打包内置**；界面不做配置/检测项，运行时直接调内置路径 |
| **ASR 模型** | 用户**可选择本机路径**（目录或文件）；保存到配置；识别前校验路径是否有效 |
| **GPU** | **自动检测**（显卡名 / CUDA）；并显示**显存总量、已用、剩余**；可「重新检测」；失败时可降级 CPU |

启动或进入识别前，真正要拦的是：**ASR 路径已配置且可用**；GPU 结果用于提示与设备选择，不是让用户手填。

检测/配置逻辑放在 **`runtime`（注册表）**，不要散落在业务积木里。

### 可拓展性约定

1. **新功能** = 新积木 + 新流水线 + 软件里加一个功能入口（页/菜单）
2. **新模型** = 注册表增加配置（id、路径、用途），ASR 等路径由用户选择或默认目录
3. **壳与业务同属 Electron**：UI 在渲染进程；流水线在主进程（`packages/core`），不写进页面组件
4. **CLI 保留**：同一套 `packages/core`（runtime + pipelines）可单独用 Node 跑，方便调试与批量，不替代软件主入口

### 交付节奏（软件视角）

1. 需求 1：软件可启动 → ASR 路径可用（+ GPU 已检测）→ 需求 1 功能页可用  
2. 需求 2：同软件内加第二功能页 + 新积木；按需扩展 TTS 等模型路径选择

## 总体架构：契约优先的流水线（搭积木）

不是「两个独立大脚本」，也不是「只把公共部分拆模块」。

约定三层：

1. **货物（Artifact）**：流水线上流转的标准数据（Video / Audio / Transcript / Translation / SRT …）
2. **积木（Module）**：只做一件事的变换 —— 输入货物 → 输出货物；不关心自己属于哪个需求
3. **流水线（Pipeline）**：需求 = 积木的组合顺序；几乎不写业务细节

```
货物（统一结构）          积木（通用能力）           流水线（需求）
Video / Audio      →   download / extract_audio  →  需求1、需求2 各自组合
Transcript         →   asr / align / export_srt
Translation        →   translate
…                  →   tts …
```

## 解决思路（总）

1. 先定货物格式（尤其 `Transcript` 必须带时间戳），再写积木。
2. 所有能力都做成通用积木；需求只负责编排组合。
3. 需求 1 跑通第一条流水线，并顺带把 `audio` / `asr` 等可复用积木做稳。
4. 需求 2 新增 `tts` / `align` / `export_srt` 等积木，新开一条流水线（内部分模式 A/B）；尽量不改旧积木内部。
5. 需求 2 两种模式：**有文案**时不以 ASR 字为准，用「文案 + 音频 → 对齐出时间轴」解决错位与断句；**仅音频**时 `asr` → 直接 `export_srt`（不跑 `align`）。

## 技术栈

### 桌面框架（已定）

**采用：`Electron` + TypeScript（业务在主进程）**

原则：**窗口与业务都用 TS**；渲染进程只做 UI，通过 IPC 调主进程能力；**不再使用 Tauri / Rust / 独立侧车进程**。

| 层 | 选型 | 语言 | 作用 |
| --- | --- | --- | --- |
| 软件外壳 | **Electron** | **TypeScript（主进程）** | 窗口、权限、对话框；加载业务 core |
| 界面 | Web 前端（Vue/React 等） | **TypeScript（渲染进程）** | 需求 1 / 需求 2 / 模型管理等页面 |
| 业务核心 | `packages/core`（主进程引用） | **TypeScript** | 模型/环境检测、调 yt-dlp、调 ffmpeg、ASR、流水线编排、进度推送 |
| 外部引擎 | yt-dlp、ffmpeg、ASR 运行时 | 二进制 / 绑定 | 不重写进业务代码 |

```
┌─────────────────────────────────────┐
│  渲染进程（TS）                       │  页面、交互
└───────────────┬─────────────────────┘
                │ IPC（推荐）/ 本地 HTTP
┌───────────────▼─────────────────────┐
│  Electron 主进程（TS）★ 主要写这里     │  窗口 + runtime / 积木 / 流水线
│    → yt-dlp / ffmpeg / ASR …         │
└─────────────────────────────────────┘
```

**主进程写什么（多写）**

- 窗口生命周期、系统对话框  
- `check_models` / `check_env`  
- `download`（调 yt-dlp）、`extract_audio`、`asr`、`translate`…  
- 需求 1 / 需求 2 流水线  

**渲染进程写什么**

- 工具箱 UI、表单、进度展示；通过 preload/IPC 调主进程，不直接 spawn 二进制  

### 业务能力（待继续锁定）

| 能力 | 倾向方向（待锁定） | 备注 |
| --- | --- | --- |
| 多平台下载 | **yt-dlp**（TS 封装调用，不重写源码） | **随软件打包**，不做用户配置项 |
| 音视频处理 | ffmpeg | **随软件打包**，不做用户配置项 |
| ASR（语音转文字） | 本地模型 + **TS/Node 绑定或可调用运行时** | 用户可选路径；须带时间戳 |
| 翻译 | LLM API 或本地模型 | 非中文 → 中文 |
| TTS（需求 2） | 待定 | 仅文案无音频时可选；也可接受外部已有音频 |
| 字幕对齐 / 断句（需求 2） | 待定 | 模式 A：贴回原文、修时间轴；模式 B：不跑 align |
| SRT 导出 | 自研小积木（TS） | 标准 `.srt` |
| 模型与环境 | runtime：ASR 路径选择 + GPU 自动检测 | yt-dlp/ffmpeg 内置不展示配置 |
